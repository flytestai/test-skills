# 禅道 Bug 写作与截图规范

> 本文件是 qa-workbench 的 Bug 提单规范，与 zentao-bug-brief-style Skill 保持一致。

## 写作原则

用户明确要求：**提单不要复杂，要简明扼要、通俗易懂，开发和测试能一眼看懂。截图必须显示在 Bug 描述最前面，不能只上传到附件。**

## 第一优先级：截图内嵌在描述最前面

1. **每条带截图的 Bug，`steps` 的第一段必须是图片**，图片要在「环境」之前，不能放在文末。
2. **只把图片上传到附件列表 = 不合格**。附件只是备份，正文必须用图片链接内嵌显示。
3. 多张截图顺序：**标注图（局部放大 + 红圈）在前，原图在后**，全部放在正文最前面。
4. 图片统一用 HTML：
   `<p><img src="https://<禅道域名>/zentao/index.php?m=file&f=read&t=png&fileID=<ID>" alt="说明" /></p>`
   优先使用绝对地址，避免相对路径在部分页面不显示。
5. **禁止**正文只写「截图见附件」「详见附件」而不放图片。
6. 写完必须回读确认：`zentao bug <ID> --pick=steps --format=json`，返回的 `steps` 开头必须是图片链接（`<img` 或 `![`），不能以「环境：」或「截图见附件」开头。

## 标准模板（带截图时照抄）

```html
<p><img src="https://<禅道域名>/zentao/index.php?m=file&f=read&t=png&fileID=<标注图ID>" alt="标注图" /></p>
<p><img src="https://<禅道域名>/zentao/index.php?m=file&f=read&t=png&fileID=<原图ID>" alt="原图" /></p>

<p>环境：好人好股V3.0.0（重构版）</p>

<p><strong>现象：</strong><一句话说清哪里不对></p>

<p><strong>复现步骤：</strong></p>
<ol>
<li>打开客户端，进入「...」；</li>
<li>点击「...」；</li>
<li>观察「...」。</li>
</ol>

<p><strong>期望：</strong><正确结果></p>
<p><strong>实际：</strong><实际结果></p>
```

没有截图时，从「环境」开始写；有截图时，图片永远在最前面。

## 带截图提单流程（必须按顺序）

1. **先起草文字**：现象 → 复现步骤 → 期望 vs 实际；不要在正文写「截图见附件」。
2. **创建 Bug 拿 ID**。如果还需要补截图，先指派给自己（当前账号），避免拿到 ID 后无法修改别人名下的 Bug。
3. **上传并内嵌截图**，优先运行本 Skill 的脚本：

```bash
node "<skill_dir>/scripts/embed_bug_screenshots.mjs" \
  --bug <BugID> \
  --image "<标注图路径>" \
  --image "<原图路径>" \
  --text-file "<正文文字文件>"
```

   脚本会：上传图片 → 取 fileID → 把 `<img>` 放在 `steps` 最前面 → 更新 Bug → 回读确认图片在开头。
   不传 `--text-file` / `--text` 时，会沿用 Bug 当前正文，只替换开头的截图。
   可先加 `--dry-run` 查看将写入的内容，不会上传、不会修改。

4. **验证**：脚本最后会输出 `stepsHead`；必须是 `<img` 或 `![` 开头。再到禅道网页打开该 Bug，确认图片实际显示出来，而不是只显示链接或 alt 文字；网页不显示时按下面「图片不显示时」处理。
5. **再指派给目标同事**：确认图片写入成功后，最后一步才改 `assignedTo`，不要一开始就指派导致无法修改。
6. **刷新 QDesk**（如果本机在运行）：

```bash
curl -s -X POST "http://127.0.0.1:4173/api/bugs/<BugID>/refresh"
```

## 图片不显示时

1. 检查 `fileID` 是否正确，图片是否能通过
   `https://<禅道域名>/zentao/index.php?m=file&f=read&t=png&fileID=<ID>` 打开；
2. 把相对路径改成绝对地址（带 `https://<禅道域名>`）后重试；
3. 如果禅道 API 把 `<img>` 转成了 Markdown `![...](...)`，先确认链接仍在 `steps` 第一行；网页仍不显示时，用禅道网页编辑器在描述最前面插入图片后保存；
4. 重新回读 `steps`，确认第一行是图片；不要用「截图见附件」代替。

## 其他硬性规则

1. **标题**：一句话讲清「在哪个页面 + 做什么操作 + 出现什么现象」，不超过 30 字。
   - 反例：`【崩溃】GUI主线程窗口重绘路径触发Qt qFatal致命终止（MainFrame.exe 0xC0000409 / Qt5Core.dll+0x1F081）`
   - 正例：`【崩溃】缩放窗口后客户端突然闪退（无任何提示）`

2. **描述只写三块**：现象 → 复现步骤 → 期望 vs 实际。能三行说清就不写五行。

3. **复现步骤 3~5 步**，每步一句话，动词开头（打开 / 点击 / 观察），必须编号。

4. **环境行固定一行**：`环境：好人好股V3.0.0（重构版）`
   需要补充机型、分辨率、账号、截图时间时，用分号接在后面，一行写完即可。

5. **技术细节一律放附件，不进正文**：调用栈、内存转储、WER 签名、日志原文、异常码、进程号、文件路径。
   正文里最多留一句「详细日志见附件」。

6. **不要**在正文写：根因分析、修复建议、影响面评估、频率放大因素、数据来源清单、符号化过程。
   这些是研发的工作，测试提单只需要把现象讲清楚。

7. **正文格式**：优先用 HTML（`<p>`、`<strong>`、`<ol>`、`<img>`）或纯文本。
   不要把 `**加粗**`、`![图片](...)` 作为唯一格式依赖；截图必须按上面的 HTML / 图片链接规则写入。

8. **只操作自己名下的 Bug**：修改、关闭、解决、激活及任何批量状态流转前，必须先确认 `assignedTo` 是当前登录账号；不是自己的 Bug 一律不操作。批量操作必须先按 `assignedTo` 过滤并报告范围。

9. **批量关闭先确认清单**：任何批量关闭前，先输出待关闭清单（至少含 Bug ID、标题、当前状态），等用户明确回复“确认执行”后再关闭。

## 创建后立即同步 QDesk

Bug 创建或补图完成后，如果本机 QDesk 正在运行，立即刷新这一条：

```bash
curl -s -X POST "http://127.0.0.1:4173/api/bugs/<BugID>/refresh"
```

若 QDesk 未启动或请求失败，忽略即可，不要因此重试创建 Bug。

## 示例（同一问题的两种写法）

**❌ 不合格：截图只在附件，正文写“截图见附件”**
```text
环境：好人好股V3.0.0（重构版）
现象：...
截图见附件。
```

**✅ 合格：截图内嵌在最前面**
```html
<p><img src="https://chandao.example.com/zentao/index.php?m=file&f=read&t=png&fileID=12345" alt="标注图" /></p>
<p><img src="https://chandao.example.com/zentao/index.php?m=file&f=read&t=png&fileID=12346" alt="原图" /></p>

<p>环境：好人好股V3.0.0（重构版）</p>
<p><strong>现象：</strong>对主窗口最大化/还原后，客户端突然闪退，无任何提示。</p>
<p><strong>复现步骤：</strong></p>
<ol>
<li>启动客户端并登录；</li>
<li>打开行情、决策、资讯页面；</li>
<li>反复最大化、还原窗口；</li>
<li>观察客户端是否突然消失。</li>
</ol>
<p><strong>期望：</strong>缩放窗口不应导致闪退。</p>
<p><strong>实际：</strong>客户端直接退出，守护进程随后自动重启。</p>
```
